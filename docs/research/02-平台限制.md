# iOS 平台限制与可用 API

> 调研日期：2026-09-26。环境：Xcode 27.0、iPhoneOS27.0.sdk、Swift 6.4。带引号的英文原文均出自 Apple 官方文档或本机 SDK 头文件。

## 结论

**第三方 App 永远无法替换 iOS 桌面。** 审核指南 2.5.8 原文：

> Apps that create **alternate desktop/home screen alternatives** will be rejected.

没有公开 API 能往桌面写图标、接管桌面点击、或枚举已安装 App。所以「大文件夹」只能做成**主屏上的一个 widget**——这是系统允许的、唯一能显示自定义内容又能响应点击的桌面元素。

一句话说清我们能做什么、不能做什么：

| | 能不能 | 依据 |
|---|---|---|
| 在桌面上放一个方块，里面画 9 个 App 图标 | ✅ | WidgetKit 自绘 |
| 点方块里的图标，打开对应 App | ✅ 但分三条路 | 见 [`01-widgetloft-拆解.md`](01-widgetloft-拆解.md) |
| 让图标出现在桌面上、和真图标一样能被拖动 | ❌ | 只有系统能画桌面图标 |
| 枚举用户装了哪些 App | ❌ 无公开 API | 见下 |
| 读别的 App 有没有通知 | ❌ 无公开 API | 已全量 grep SDK 确认 |
| 用自己的图标替换别人的图标 | ❌ | 只能画在自己的 widget 里 |

## 一、widget 能打开什么

### 1.1 `Link` / `widgetURL` 只能打开宿主 App

Apple 文档 *Linking to specific app scenes from your widget or Live Activity* 原文：

> When the widget or Live Activity receives an interaction, the system **activates the containing app** and passes the URL to `onOpenURL`.

SwiftUI 的 `View.widgetURL(_:)` 参数说明同样是 "The URL to open **in the containing app**."

两条附带限制：

- 一个 widget 视图层级里**只能有一个** `widgetURL`，多个时行为未定义 → 所以「多格子」只能用 `Link` 或 `Button`。
- `Link` 在 `systemSmall` 上不提供独立点击区，需要 medium 及以上。

### 1.2 `Button(intent:)` 可以，但打开了「另一个 App」这条路要 iOS 27

iOS 17 引入了交互式 widget，但 Apple 在同一篇文档里给了明确的态度：

> An interaction with a button or toggle **should do more than open the app**. If you want to offer an interaction that opens the app, use `Link` and `widgetURL(_:)`.

也就是说 iOS 17–26 期间，**Button + AppIntent 不是用来「开 App」的**。iOS 27 的 `RunSystemShortcutIntent` 才把这个用途正式纳入。

### 1.3 `OpenURLIntent` 走通用链接，不吃自定义 scheme

`OpenURLIntent`（iOS 18.0+）让 intent 返回一个「请系统打开这个 URL」的结果：

```swift
public func perform() async throws -> some IntentResult {
    .result(opensIntent: OpenURLIntent(url))
}
```

关键限制在 `URLRepresentableIntent` 的文档里：

> This protocol requires your app to support universal links. **You can't use this protocol with a custom URL scheme** or other approaches.

所以我们用它打开 `weixin://` 是没用的——必须 `https://` 且目标 App 声明了该域名的 associated domain。

### 1.4 iOS 27 的 `RunSystemShortcutIntent`

见 [`01-widgetloft-拆解.md`](01-widgetloft-拆解.md#③-系统代持ios-27官方正解)。本机 SDK 确认：

```
@available(iOS 27.0, *) @available(macOS, unavailable) @available(tvOS, unavailable)
@available(watchOS, unavailable) @available(visionOS, unavailable)
public struct RunSystemShortcutIntent : AppIntents::SystemIntent {
  public init(shortcut: AppIntents::SystemShortcut)
  ...
}
```

`SystemShortcut` 在 SDK 里就是一个空结构体 + `displayRepresentation`，**没有任何可构造、可枚举的入口**。目标由用户在 widget 配置界面里选。

### 1.5 `ForegroundContinuableIntent` 在 widget 扩展里不可用

本机 SDK：

```
@available(iOS, introduced: 16.4, deprecated: 26.0, ...)
@available(iOSApplicationExtension, unavailable)
public protocol ForegroundContinuableIntent : AppIntents::AppIntent {}
```

`@available(iOSApplicationExtension, unavailable)` 意味着 **widget 扩展里根本编译不过**。iOS 26 起它被 `supportedModes` 取代：

```swift
@available(anyAppleOS 26.0, *)
public static var supportedModes: IntentModes { get }   // .background | .foreground(.immediate/.dynamic/.deferred)
```

`openAppWhenRun` 同样在 iOS 26 被弃用：

```
@available(iOS, deprecated: 26.0, message: "Please provide 'supportedModes' instead")
static var openAppWhenRun: Bool { get }
```

> 对我们的意义：`openAppWhenRun` / `supportedModes` 决定的是**要不要把自己的 App 提到前台**，不是别人的。中转路线的原理正是「把自己的 App 提起来，再由它跳走」，所以我们在 App 进程里用 `UIApplication.open` 就够了，不需要碰这些。

## 二、`LSApplicationQueriesSchemes` 的上限（重要）

Apple 在 `canOpenURL(_:)` 文档里写明了两件事，第一件是限制，第二件是**逃生口**：

> Apps linked on or after iOS 15 are limited to a maximum of **50 entries** in the `LSApplicationQueriesSchemes` key. Apps linked on or after iOS 27 are limited to a maximum of **25 entries** in the `LSApplicationQueriesSchemes` key.
>
> Unlike this method, the **`open(_:options:completionHandler:)` method isn't constrained by the `LSApplicationQueriesSchemes` requirement**. If an app is available to handle the URL, the system will launch it, even if you haven't declared the scheme.

> 翻译成人话：**25 条上限只管「问」，不管「开」。**

这直接决定了架构：

- 判断「这个 App 装没装」→ 受 25 条预算限制 → 只能留给最常用的 App
- 打开一个 App → **不受限** → 目录可以无限大，用户想加什么都能加

另外，`canOpenURL` 在 iOS 27 被标记废弃：

```
- (BOOL)canOpenURL:(NSURL *)url API_DEPRECATED("Prefer attempting to open URLs and handling any failures", ios(3.0, 27.0), ...)
```

Apple 的建议是**直接尝试打开，处理失败**。所以我们的探测只用来给 picker 打「已安装」标签，不用来做任何关键判断。

## 三、枚举已安装 App：没有合法途径

| 途径 | 能给什么 | 门槛 |
|---|---|---|
| `LSApplicationWorkspace`（私有） | 全部 App + bundle id | **会被拒**，iOS 11 起已失效 |
| `FamilyActivityPicker`（iOS 15+） | 不透明 token，能渲染图标 | 需 Family Controls entitlement（Apple 人工审批） |
| `FamilyActivityData.installedApplications`（iOS 26.4+） | **真实 bundleIdentifier** | 同上，且**仅 EU 可用** |
| `MarketplaceKit.AppLibrary`（iOS 17.4+） | 已安装 App 列表 | **仅 EU** |
| 解析系统「分析数据」文件 | bundle id 列表 | 需要用户手动去设置里导出（MiniFolder 走的这条） |

`FamilyActivityPicker` 看着最像答案，但 Apple 的定位说明堵死了它：

> A view in which users specify applications, web domains, and categories **without revealing their choices to the app**.

它给你 token，不给你 bundle id；`Label(token)` 能画出真实图标，但你**换不到 scheme，也就打不开**。加上 entitlement 需要单独申请、且审核定位是家长控制，拿它当「App 选择器」风险很高。

**结论：走策展目录 + 用户手动搜索。** 这也正是 WidgetLoft「A bigger app catalog」在做的事。

### 复核（对整个 iPhoneOS27.0.sdk 做了一遍穷举）

上面这张表是查文档得来的。后来把 SDK 里 225 个 `.swiftinterface` 全部 grep 了一遍做复核，结论不变，但有几点值得补：

- **`FamilyActivityData.installedApplications` 是 iOS 26.4 才有的**，比 iOS 18 新——也就是说 Apple 这几年唯一一次真正给出「已安装 App 列表」的动作，就是它。
- **门槛比原先写的更严一层。** 需要的是**第二个独立 entitlement**：`com.apple.developer.family-controls.app-and-website-usage`（「Family Controls App & Website Usage」）。Xcode 的能力库里标着 `isPublic: true` 但 **`canRequestFromPortal: false`**，也就是不能通过开发者门户自助申请。另外还要 `AuthorizationCenter` 运行时授权，新加的 `AuthorizationStatus.approvedWithDataAccess` 才是真正放行数据的状态。
- **SDK 里从头到尾没出现过「EU」这个词。** 原文只有一句 `To access data, the user must be in a region that supports data access.`。地区限制是真的，但「就是欧盟」这个说法在 SDK 里找不到出处——是二手资料的说法。
- **`ManagedSettings.Application` 的 `bundleIdentifier` 和 `localizedDisplayName` 在你自己的 App 里是 `nil`**，只有在「提供 shield 配置的扩展」里才有值。所以就算你合法拿到了 token，也换不到 bundle id。原文：*"When you access this property outside that extension, the value is `nil`."*
- **`canOpenURL` 在 iOS 27 被正式废弃**（`API_DEPRECATED ios(3.0, 27.0)`）。这恰好是我们唯一的探测手段，见 ``AppCatalog`` 里的实测记录。

有两个 API **正是我们想要的，但不公开**——它们在 `.tbd` 里有导出符号，却完全不在 `.swiftinterface` 里：

| 符号 | 作用 |
|---|---|
| `AppIntents.IntentApplication` | 「App 作为一个 intent 值」：`init(bundleIdentifier:)`、`bundleIdentifier`、`rawValue`，还有 `IntentApplicationFromStringResolver` 和一个 `SystemFrameworkIntent.app` 访问器 |
| `AppManagedFeatures.ApplicationFiltering.installedUserVisibleApplications` | 字面意思就是「返回已安装的可见 App 的 (bundleID, name) 列表」 |

用不公开的 API 等于上架即被拒，所以这两条只做为记录——但它们说明 Apple 内部有这套能力，只是不给第三方。


## 四、图标：可以显示别人的图标，但要绕

widget 里**不能**读别的 App 的图标（沙箱）。两条可行路径：

1. **iTunes Search API**（WidgetLoft 隐私政策原文：*"App icon artwork may be fetched from the public iTunes Search service to render icons"*）——拿到 App Store 的 `artworkUrl512`，缓存到 App Group。
2. **用户自选图片**——需要用户自己去截图/找图。

竞品 Cromulent Launcher 的说法印证了这条限制：

> **Apple does not give widgets access to the icons of other apps**, so Launcher has to guess the icon based on the app's name.

第 1 条是我们已经在做的（`IconStore`）。注意它有个必要前提：**目录条目必须有 App Store id**，否则拿不到图标。

## 五、审核风险

| 条款 | 原文 | 对我们的风险 |
|---|---|---|
| **2.5.8** | Apps that create alternate desktop/home screen environments will be rejected. | **低**——我们不是替代桌面，只是在桌面上放一个 widget |
| **2.5.16** | Widgets, extensions, and notifications should be related to the content and functionality of your app. | **中**——widget 必须展示 App 自己的数据（我们的「文件夹」是自己管理的，天然相关） |
| **3.2.2(i)** | Creating an interface for displaying third-party apps… similar to the App Store or as a general-interest collection. | **中**——我们的 picker 是「选择要放到桌面的图标」，不是商店式浏览，不能做成推荐/排行/展示价格 |
| **4.2 / 4.2.2** | …apps shouldn't primarily be … content aggregators, or **a collection of links**. | **高**——如果宿主 App 只是个「配置器」，很容易被这条打 |

**历史判例**：2014 年的 `OpenIt` 作者在 README 里写过 "after seeing other launcher apps being rejected (or approved and then removed), I decided to open source the project." 但近年的竞品（WidgetLoft、Launcher、Lock Launcher、MiniFolder）都在架且持续更新，Apple 事实上默许了这个品类。

**规避方式**（也是 WidgetLoft 后半段更新在做的事）：让宿主 App 自己是个独立产品——图标工作室、标签与归档、备份导出、内置指南。**不能让用户觉得「装这个 App 只是为了拿一个 widget」。**

## 六、iOS 27 新增（与我们相关）

本机 SDK 全量扫描的增量：

| API | 可用性 | 用途 |
|---|---|---|
| `WidgetFamily.systemExtraLargePortrait` | iOS 27.0 | **整页大小的主屏 widget**（WidgetLoft 的「77 个 App」靠它） |
| `RunSystemShortcutIntent` / `SystemShortcut` | iOS 27.0 | 系统代持的直开 |
| `IntentExecutionTargets` | iOS 27.0 | 指定 intent 在哪个进程跑（`main` / `appIntentsExtension` / `widgetKitExtension`） |
| `EnvironmentValues.isDynamicIslandLimitedInWidth` | iOS 27.0 | 灵动岛布局 |
| `FamilyActivityData` | iOS 26.4 | 枚举已装 App（EU + 审批） |

**没有**新增的：任何能读他人通知/角标的 API。全 SDK grep 确认。

## 七、分发备选

如果 App Store 被拒：

| 途径 | 限制 |
|---|---|
| TestFlight | 外测 10,000 人 / 内测 100 人 / 构建 90 天过期 / 首个构建需审核 |
| 免费 Apple ID 自签 | **7 天过期**、10 个 App ID/周、3 台设备、每设备 3 个 App、**没有 App Group** ← 对本项目致命 |
| AltStore / SideStore | 同样是 7 天周期；SideStore 免电脑 |
| AltStore PAL | 仅 EU / 日本 / 巴西，无过期无数量限制，需公证 |
| 付费开发者 $99/年 | 365 天 profile、可 ad-hoc、TestFlight |

> **免费自签没有 App Group**，意味着宿主 App 和 widget 无法共享存储——我们的 widget 会渲染成空。这是 `FolderStore` 里有降级路径、设置页会显示「App Group 不可用」的原因。
