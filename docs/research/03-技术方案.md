# AppFolder 技术方案

> 基于 [`01-widgetloft-拆解.md`](01-widgetloft-拆解.md) 与 [`02-平台限制.md`](02-平台限制.md) 的结论。当前代码已经按这份方案实现。

## 一句话

既然 iOS 不允许第三方 App 接管桌面，那就把「大文件夹」做成**主屏上的一个 widget**：方块里平铺 4–9 个真实 App 图标，点一下打开对应 App——能直开就直开，不能就中转，由每条图块自己记着该走哪条路。

## 架构

```
AppFolder.app                    AppFolderWidget.appex
  ├─ LibraryModel ──┐              ├─ FolderTimelineProvider
  ├─ InstallationProber            │    └─ 读 FolderStore
  ├─ IconStore      │              └─ FolderWidgetView
  └─ FolderEditor   │                   ├─ Link        (bounce)
        │           │                   └─ Button      (universalLink)
        ▼           ▼                        │
   ┌──────────────────────────────────────────┴───┐
   │  AppFolderKit（本地 Swift Package）           │
   │  Folder / FolderStore / AppCatalog /         │
   │  LaunchStrategy / LaunchLink / OpenLinkIntent │
   └───────────────────────────────────────────────┘
                    │
                    ▼
        App Group: group.com.lvyufeng.appfolder
          library.json   ← 文件夹定义
          Icons/         ← 缓存的真实图标
          UserDefaults   ← widget 展开状态
```

**为什么核心逻辑放在 Swift Package 而不是直接放两个 target：** 因为 `AppIntent` 必须同时被 widget 扩展（`Button(intent:)` 调用它）和宿主 App（跳转）看到，两条 target 各编译一份同样的类型是 bug 的温床。一个本地 package 让「只有一份定义」变成编译期保证。

## 打开一条图块：三条路

这是整个产品的核心，也是调研花时间最多的地方。详见 [`01-widgetloft-拆解.md`](01-widgetloft-拆解.md)。

| 策略 | 实现 | 生效条件 | 有无闪烁 |
|---|---|---|---|
| `universalLink` | `Button(intent: OpenLinkIntent)` → `OpenURLIntent` | 目标是 `https://` 且目标 App 声明了该域名 | **无** |
| `bounce` | `Link(destination: appfolder://launch?u=<target>)` → 宿主 `UIApplication.open` | 总是 | **有，闪一下 AppFolder** |
| `systemShortcut` | `Button(intent: RunSystemShortcutIntent)` | iOS 27+，且用户在小组件配置里手选 | **无** |

**默认是 `bounce`。** 理由：它是唯一对任何目标都成立的路线。`universalLink` 是优化——能用的目标不多（大多数 App 只暴露自定义 scheme），但用上了就没有切换感。`systemShortcut` 撑不起网格（系统只给「一个配置位一个动作」），留给「我最常用的一个 App」这种单图块 widget。

`LaunchStrategy` 存在**每条图块**上，不是每个文件夹，因为该走哪条路取决于目标 URL 的形态而不是它被放在哪个文件夹。

### 为什么不让用户「试一下自动选」

因为**直开失败的图块没有任何反馈**。`Button(intent:)` 在扩展进程里跑，系统丢掉结果，不回传成功或失败。一次什么都没发生的点击，和一次成功的点击，从 widget 内部看完全一样。

所以本 App 的做法是：**把选择权交给用户，并提供验证入口**。编辑器里每条图块都有「试一下」按钮——它调用 `canOpenURL` / `open` 回答一个**能回答的问题**（这个 URL 在这台设备上打得开吗？），而不是假装能测出 widget 那条路。测试结果和说明文字直接写在图块下面。

## 已安装 App 的发现

**没有合法途径枚举已安装 App**（详见 [`02-平台限制.md`](02-平台限制.md#三枚举已安装-app没有合法途径)）。我们的做法：

1. 内置一份**策展目录**（`AppCatalog+Data.swift`，约 60 个中英常用 App，含中文名、英文名、URL scheme、App Store id）
2. 用 `canOpenURL` 逐个探测，给 picker 打上「已安装」分组
3. 目录之外的目标，用户可以手填 URL

**关键约束**：`canOpenURL` 的预算只有 **25 条**（iOS 27 链接的 App；iOS 15 是 50）。而 `open(_:)` **不受限**。

所以 `AppCatalog.queriedSchemes` 只取 `selectable` 里 `appStoreID != nil` 的条目（就是那些能显示真实图标的），恰好控制在预算内；而**目录本身可以无限大**——不在探测名单里的 App 依然能打开，只是 picker 不给它打「已安装」标签。

`tools/generate-queried-schemes.swift` 保证 `Info.plist` 和目录不跑偏：

```
swift run --package-package-path Packages/AppFolderKit appfolder-schemes        # 打印要粘的片段
swift run --package-path Packages/AppFolderKit appfolder-schemes --check        # CI 用，不一致就非零退出
```

## 图标

widget 沙箱读不到别的 App 的图标，只能自己拿。两条路：

1. **iTunes Search API**（`IconStore`）——按 App Store id 拿 `artworkUrl512`，缓存到 App Group 的 `Icons/`。这是 WidgetLoft 隐私政策自己写明的做法，也是唯一能拿到「本尊图标」的合法途径。
2. **用户自选图片**——`FolderTile.customIconName` 指向 App Group 里的一份 PNG。

缓存放 App Group 是因为 widget 也要读。`WidgetIconCache`（widget 侧）不做网络请求——时间线刷新的预算很紧，下载是宿主 App 的活。

## 文件夹展开

「点文件夹，在里面展开」不是系统能力，是**用交互式 widget 伪造的**：

1. 图块绑 `Button(intent: ToggleFolderIntent)`
2. intent 把「当前展开哪个文件夹」写进 App Group 的 UserDefaults
3. 调 `WidgetCenter.reloadAllTimelines()`
4. 新渲染的时间线画的是子内容 + 返回图块

代价是**点击到重绘之间有一拍**，且刷新时机由系统决定。我们保留旧帧的文件夹标题就是为了让这一拍读起来像过渡而不是卡顿。WidgetLoft 的更新日志印证了这是这套机制的固有瓶颈（2.1.1："The blank space and the stalling seen in widgets with many apps are fixed"）。

## 关于 App Group 与免费自签

免费 Apple ID 签名**不能开 App Groups**，宿主和 widget 就没有共享存储，widget 会渲染成空。`FolderStore` 因此有两级存储：App Group 容器为主，`UserDefaults` 兜底（仅让宿主自己能跑）。设置页会显示「App Group：可用/不可用」，因为这问题否则完全不可见、且看起来就像 App 坏了。

## 版本目标

- **最低 iOS 18.0**（与 WidgetLoft 一致）。`Button(intent:)` 要 17，`OpenURLIntent` 要 18；18 同时带来 tinted 图标渲染的完整支持。
- **iOS 27 分支增强**：`systemExtraLargePortrait`（整页 widget）、`RunSystemShortcutIntent`（无闪烁直开）。这些都是 `@available(iOS 27.0, *)`，不影响 18 的编译。

## 还没做

按优先级：

1. **中转的观感优化**——让 AppFolder 在跳转时尽量「隐形」（无动画的空白窗口）。这是体验分水岭，WidgetLoft 花了好几个版本在这上面。2026-09-27 逐帧测过：中转全程 ≈ 4.2s，其中我们自己能压的只有那 ≈ 0.45s 的空白屏，其余 92% 是目标 App 冷启动本身（黑屏 2.5s + 渲染 1.5s），和直接从桌面启动它一模一样。数字见 [`04-实现笔记.md`](04-实现笔记.md) 第四节。
2. **文件夹嵌套**——数据模型要改成树，编辑器要重做。
3. **备份导出 / iCloud 同步**——`FolderLibrary` 已经是 Codable，导出是顺手的事。
4. **图标工作室**——自选照片/符号/文字。属于「让宿主 App 有内容」的合规投资。
5. **批量导入**——先看用户抱怨什么。WidgetLoft 到 2.1.2 才做，且很可能只是多选 UI 的优化。
6. **通知红点**——无法用 API 实现，只能靠快捷指令自动化，优先级最低。

以及一条现在清楚了、但暂时不值得做的：**给更多苹果自家 App 找通用链接**。测下来只有地图和新闻有（见 `04-实现笔记.md`），其余一律落 Safari，所以目录里系统 App 的默认路线就是中转。要加就得先实测出一个「落在 App 且不拖 Safari」的 URL——`?t=m` 这种是试出来的，不是推出来的。

另一条待真机验证的：`ximalaya.mainapp://`、`fleamarket://`、`wemeet://`、`baiduboxapp://` 这四个「待验证」条目的 scheme，模拟器上装不了 App，判不了。
