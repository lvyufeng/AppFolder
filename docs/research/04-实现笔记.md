## 一、`.bounce` 的真实代价（已更正：没有确认弹窗）

> **2026-09-27 更正。** 这一节原先写的是「iOS 27 对自定义 scheme 拉起宿主 App 加了确认弹窗，点一个图块要两次点击」。**重放下来这个结论是错的**，弹窗不存在。下面留着原始记录，然后是重放的证据和错在哪。

### 原文（已推翻）

技术方案里把 `.bounce` 写成「宿主 App 闪一下」。最初的实测说不是闪一下：在 iOS 27 模拟器上执行

```
xcrun simctl openurl <device> "appfolder://launch?u=shortcuts%3A%2F%2F"
```

屏幕上出现一个居中模态弹窗「在「AppFolder」中打开？［取消］［打开］」，还配了对照——`maps://`、`shortcuts://` 直接打开都没有弹窗。

### 重放：三次，都没有弹窗

同一条命令，同一条模拟器，每次先把 `AppFolder` 和 `Shortcuts` 都 terminate，再录屏 12fps 逐帧判读。三次的形状完全一致：

| 时间（相对发令） | 屏幕 |
|---|---|
| 0.08–0.58s | AppFolder 的空白屏（`Color(.systemBackground)`，这是 `.bounce` 的刻意的「什么都不画」） |
| 0.67–1.00s | 回到桌面 |
| 1.08–2.91s | 全黑（Shortcuts 在冷启动） |
| 3.00s 起 | 「所有快捷指令」页 |

**弹窗一帧都没有。** 判据不是肉眼看缩略图：我写了个弹窗检测器（屏幕中央 40% 与左右边缘的亮度差），在整段录屏里逐帧跑，峰值差异 0.07——和对照组（已知会正常走到 Safari 的那批）的数值一模一样，也就是「没有弹窗」的基线。

对照：同一条命令把目标换成 `https://time.is`，链路是「空白屏 → 黑屏 → Safari 首帧」，中间同样没有任何确认。

### 错在哪

原来那次测到的弹窗是**真的**，但它不是 `simctl openurl` 弹的，而是**上一条 `simctl privacy <device> grant all <bundle>` 弹的**——「grant all」会请求一堆权限，系统为其中某一项发一个确认框。两条命令挨着执行，弹窗在时间上落在第二条后面，就被归因给了它。

复现这个坑：先 `simctl privacy … grant all`，紧接着截图，就能拿到那个弹窗；干净重装之后只发 `openurl`，弹窗不再出现。

**留给下次的教训**：`simctl` 的两条相邻命令之间，屏幕状态不能默认是干净的。要判定「某个操作是否弹窗」，操作前后必须各有一次截图，而不是只截操作之后。

### 所以 `.bounce` 现在的成本

只剩「一次可见的跳转」，没有第二次点击。仍然是三条路线里最慢、最显眼的一条（见下面第三节的实测数字），但它是可用的，不需要退回 `.systemShortcut`。

## 二、App Group 从来没生效过——但症状完全不像

### 症状

App 跑在模拟器上，文件夹列表是空的，尽管共享容器里有数据。

### 排查过程（以及一条错误的中间结论）

1. `codesign -d --entitlements :- AppFolder.app` → `{}`。看起来像签名没带上 entitlement。
2. 检查 pbxproj，`CODE_SIGN_ENTITLEMENTS` 四处都在，指向的文件存在。
3. 改签：`CODE_SIGN_IDENTITY="-" CODE_SIGNING_REQUIRED=YES` → 依然 `{}`。
4. 于是写了脚本直接从二进制里挖 `__TEXT,__entitlements` section（`otool -s` 的输出是**按 4 字节倒序**的，要转换回来）：

```
app:    application-identifier = FAKETEAMID.com.lvyufeng.appfolder
        com.apple.security.application-groups = [group.com.lvyufeng.appfolder]
widget: application-identifier = FAKETEAMID.com.lvyufeng.appfolder.widget
        com.apple.security.application-groups = [group.com.lvyufeng.appfolder]
```

**entitlement 一直都在。** `codesign -d` 读的是 `__LINKEDIT` 里的签名 blob，而模拟器构建用的是 `-no_adhoc_codesign`，那边本来就是空的。看错了地方，得出了错的结论。

5. 装到模拟器上、启动 App，然后扫 `Containers/Shared/AppGroup/` 里的 metadata：

```
group.com.lvyufeng.appfolder -> .../Shared/AppGroup/BC5E3D45-...
```

容器被创建了，说明 `containerURL(forSecurityApplicationGroupIdentifier:)` 真的拿到了路径。

### 真正的原因

容器里躺着一个 `library.json.corrupt`，内容是**手写进去的测试文件夹**。

为了往模拟器里塞测试数据，我直接写了 `library.json`，日期用的是 ISO-8601 字符串（`"2026-09-26T16:48:00Z"`）——因为那是人写 JSON 时的自然写法，也是 `ISO8601DateFormatter` 的输出。

而 `JSONDecoder` 的**默认**日期策略是「自 2001-01-01 起的秒数」，不认字符串。于是 `Folder.updatedAt` 解析失败 → **整个 `FolderLibrary` 解码失败** → `FolderStore.load()` 走 catch 分支 → 把文件改名成 `.corrupt` → 返回 `.empty`。

九块图块的文件夹，因为一个时间戳格式，被当成损坏文件隔离并清空了。

### 值得记下来的三点

- **不要在错误的地方找证据。** `codesign -d` 返回 `{}` 是模拟器构建的**正常**行为，不是 bug。花了最多时间的一条线索从头到尾都是假的。
- **`JSONDecoder` 的默认日期策略是个陷阱。** 它不是「宽松解析」，是「只认一种格式」。任何手工编辑、导出、或别的工具生成的文件都会踩到。
- **静默的数据丢弃比崩溃更糟。** 隔离再清空的行为本身是对的（widget 不能崩），但它没有留下任何用户可见的痕迹。

### 修法

新增 `FolderCoding`，成为磁盘格式的唯一定义：

- 编码保持原样（默认策略），因为那是跟已经躺在磁盘上的文件之间的契约；
- 解码接受**两种**：数字（我们写的）和 ISO-8601 字符串（别人写的、手写的、将来导出的）；
- 拒绝时给出可读的错误信息，说明期望的是哪两种格式。

配套 `AppFolderKitTests/FolderCodingTests.swift`，8 条测试覆盖：两种日期格式、往返、缺字段容错、以及「只对问过且答否的 scheme 判定不可达」。

## 三、App Store ID 里有四个是假的

`腾讯会议` 的 `appStoreID` 是 `1478568808`。用 iTunes Search API 查这个 id，返回的是一个**音乐单曲**：

```
"kind": "song", "trackName": "Adagio, 3/4 Albinoni Adagio for Strings 2nd Side (Live)"
```

后果会很难看：图块会画出唱片封面，点开却是腾讯会议。而且因为 `lookup` 接口"有结果就返回"，代码里没有任何一处会察觉这件事。

逐条核对 59 个 id 之后，一共 14 个是错的——多数是**差几位的那种抄写错误**（`930434564` vs 真实值 `930368978`），这种错误看起来极其合理，只有查了才知道。

### 修法：把检查变成命令

`appfolder-schemes --verify-ids`：

- 逐条查 `itunes.apple.com/lookup`（CN 区 / US 区按名字是不是 ASCII 判断）；
- **error**：无结果、`kind != "software"`、返回的 `trackId` 和请求的不一致；
- **warning**：查到了、是 App、但上架名和我们的名字对不上——因为改名确实会发生（`饿了么` 现在的上架名是 `淘宝闪购-点外卖更优惠`），这种情况需要人看一眼而不是直接失败；
- Apple 会限流，所以每条之间 sleep 1.2s、失败重试 3 次；「查不到」和「网络不通」是两种不同的结论，分开报。

注入两个真实的错误（把 id 改回去）验证过：两条 error、退出码 1。59 个 id 现在 0 error / 1 warning。

## 四、`.bounce` 路线现在长这样

原来的实现是「打开 AppFolder → 立刻转出去」，问题在于中间那一帧：文件夹列表会完整渲染、滚动到位，然后被撕掉。不但更慢，而且一眼就看出「这不是我要打开的 App」。

`BounceRouter` 做的两件事：

1. **收到的当回合就转出去**——不读 library、不解析图标、不等 model 加载完。
2. **转出期间画一块纯色**，`RootView` 在 `isHandingOff` 为真时只画一个空白面。看起来像目标 App 启动得慢，而不是 AppFolder 冒出来又消失。

摘掉这块遮罩的时机是唯一微妙的地方，每个"简单"的写法都是 bug：

- 在 `open` 的回调里报告成功就摘 → 会闪。`success == true` 只代表系统**接受**了这个请求，此刻 AppFolder 还在前台。
- 在下次 `scenePhase == .active` 时摘 → 也会闪。App 是**先**经过 `.active` 才进 `.background` 的，等于出门前先把家收拾了。

所以只在「已经去过后台、又回到前台」时才摘——那是目标 App 确实接管过的唯一证据。兜底是一个 3 秒超时：handle 没有接手（scheme 没有 App、或者系统拒绝了），用户拿回启动器，而不是永远对着一块白屏。

### 逐帧测出来的时间线（2026-09-27）

用 `simctl io recordVideo` 录屏 + 自写的逐帧分类器，把一次冷启动中转拆开。目标是 `https://time.is`（走 Safari，因为模拟器上没有第三方 App），Debug 和 Release 各三次：

| 阶段 | 时长 | 谁在画 |
|---|---|---|
| 点下去 → AppFolder 的空白屏出现 | ≈ 0.4s | 系统启动 AppFolder |
| 空白屏挂住 | ≈ 0.45s | AppFolder，`Color(.systemBackground)` |
| 退回桌面 | ≈ 0.35s | 系统在交接 |
| 全黑 | **≈ 2.5s（最大的一块）** | Safari 冷启动 |
| 黑屏里浮现出页面 | ≈ 1.5s | Safari 渲染 |
| **合计：页头画出来** | **≈ 4.2s** | |

Release 和 Debug 一样（4.25s vs 4.16s，在噪声内）——所以这不是我们没开优化，**大头是 Safari 的冷启动**，那 2.5 秒的黑屏不管我们怎么写都在。

我们真正能压的只有中间那 ≈ 0.45s 的空白屏（缩短超时、在 `.background` 一发生就摘遮罩，而不是等回到 `.active`）：省下 ≈ 0.35s，占总时长 8%。剩下 92% 是「目标 App 冷启动」这件事本身的成本。

对照：不走中转、直接从桌面冷启动 Safari 打开同一个网址，黑屏同样是 ≈ 4s。**也就是说中转并没有让启动变慢，它只是把「Safari 本来就要花的时间」前面加了一段我们自己的、看得见的 0.45 秒。** 这解释了为什么这 0.45 秒在体感上比它的实际占比更刺眼——它出现在用户刚点完的那一刻。

对照的数字要按同一把尺子读：从桌面直达 Safari，Safari 首帧在 4.0s；经中转，TIME.IS 页头在 4.16–4.25s。两者只差一次桌面往返，中转本身（AppFolder 的启动 + 跳转）几乎不占时间。

## 五、模拟器上验不了的东西

诚实记一笔，免得下次以为这些验过了：

| 想验的 | 为什么验不了 |
|---|---|
| 点图块的实际行为 | `simctl` 没有点击模拟器 UI 的工具，也没有 `idb`；widget 里的 `Link` 点了会怎样只能真机点 |
| 真机上 `LSApplicationQueriesSchemes` 是否真的生效 | 模拟器上没有一个目标 App 是装着的，`installedSchemes` 永远是空集 |
| 图标外观四档下 widget 底板的样子 | 切那一档要进入「编辑 → 自定」。**2026-09-27 找过了**：那不是一条 `defaults` 键，是 Home Screen poster 配置的一部分，没被改过就不落盘，也没有无头写入的办法——所以四条都不是「没找到开关」，是「这台机器改不了」。仍要真机，见「默认档那一格，模拟器答不了」 |

**2026-09-27 划掉一条**：上面原本还有一行「widget 在桌面上的实际渲染」，理由写的是「`simctl` 没有添加 widget 的子命令」——**这条是错的**。`IconState.plist` 就是桌面的布局文件，手工往第 0 页插一个 widget 条目再重启模拟器，桌面就会真的渲染它，而且能量像素。下面三节里所有关于底板颜色的结论都是这么量出来的，方法写在「什么时候重画」那一段末尾。

模拟器上能验证的：App 的界面、共享容器的读写、解码路径、bounce 的 URL 编解码与路由逻辑、`appfolder-schemes --check` / `--verify-ids`、**桌面上 widget 的实际渲染与像素读数**，以及——**2026-09-27 补上**——中转的完整链路和耗时。

**中转链路是怎么在模拟器上验的**：用 `xcrun simctl openurl` 发一条真正由 widget 发出的那种 URL（`appfolder://launch?u=…`），再用 `simctl io recordVideo` 录屏逐帧判读。这条路走的是和 widget 的 `Link` 完全相同的系统入口（`onOpenURL`），所以「弹窗在不在」「耗多久」这两个问题它答得了。它答不了的是「widget 的 `Link` 会不会和 URL 走同一条路」——那一条仍然要真机点。

那个「确认弹窗」的旧结论就是这么被推翻的，见第一节。

## 六、`LSApplicationQueriesSchemes` 到底管什么（实测）

这一节是实验测出来的，不是读文档读出来的。三条结论都有反例可复核。

### 实验一：声明超过 25 条会怎样

在 catalog 最前面插两个探针（`maps://`、`shortcuts://`），把 `queryBudget` 改成 60，生成 57 条声明写进 Info.plist。结果：

```
probed:  57   installed: ['maps', 'shortcuts']
  maps (pos 56):      probed? True  installed? True
  shortcuts (pos 57): probed? True  installed? True
```

**全部 57 条都生效，包括第 56、57 条。** 文档里写的 25 条上限并没有以「丢弃超出的条目」的形式执行——至少模拟器上不是。

### 实验二：没声明的 scheme 能不能问

这才是关键的一条。第二个实验直接问 `maps`（已声明、设备上有）、`music`（未声明、设备上没有）、以及一个专门为此写的测试 App 的 scheme。

为了有个可控的「装了但没声明」的样本，临时编了一个最小 iOS App：

```
clang -target arm64-apple-ios18.0-simulator -isysroot $SDK -framework UIKit -fobjc-arc ...
```

它的 `CFBundleURLSchemes` 是 `afprobe1` / `afprobe2`，`simctl openurl afprobe1://` 能打开它，确认装好了。然后让 AppFolder 去问这些 scheme：

```
installed: ['maps', 'photos-redirect', 'shortcuts']
  maps             installed=True      (已声明)
  shortcuts        installed=True      (已声明)
  photos-redirect  installed=True      (已声明)
  music            installed=False     (未声明)
  afprobe1         installed=False     (未声明，但确实装了)
  afprobe2         installed=False     (未声明，但确实装了)
  afprobenope      installed=False     (未声明)
```

**唯一为真的都是已声明的。** 一个确实装着的第三方 App，只要 scheme 没写进 plist，`canOpenURL` 一律回 `false`。

四象限：

| 已声明 | 有处理者 | `canOpenURL` |
|---|---|---|
| 是 | 是 | `true` |
| 是 | 否 | `false` |
| 否 | 是 | `false` |
| 否 | 否 | `false` |

### 结论

- **没有免费午餐。** 想用 `canOpenURL` 发现已安装的 App，就必须把它的 scheme 写进 plist。第三条路不存在。
- **上限不该被当成「多写也没用」**（实验一），但也不该被利用：超过 25 条就依赖一个 Apple 明确写了、只是当前没执行的行为，未来某个版本收紧就直接坏掉。所以 `queryBudget` 留在 25。
- **「没问过」必须和「问过、答否」分开。** 这一点在 UI 上体现为选择器的三段式：已安装 / 其他 / 未安装。之前只有两段，等于把「系统不让我问」显示成了「你没装」。

（顺带一提：`weixin://`、`snssdk1128://` 这类在模拟器上打不开，`simctl openurl` 会报 `LSApplicationWorkspaceErrorDomain error 115`。模拟器上一个第三方 App 都没装，所以模拟器里「已安装」永远是空的——这一段的验证必须在真机上做。）

## 「直接打开」为什么点不动（地图那个 bug）

用户报的：**「我把地图配置成了直接打开，但是点击之后会进入 app 而不是直接打开」。**

### 现象与根因

先看存下来的库，地图那一格长这样：

```
地图   url=maps://   strategy=universalLink
```

`OpenLinkIntent(tile:)` 会把任何非 http(s) 的 URL 拒掉，`maps://` 直接被拒 → `TileButton` 落到那个「画个图标、不响应」的分支 → **点下去什么都不会发生**。

这里没有任何报错。文件能读、图标能画、时间线正常、`perform()` 根本没被调到。这就是这类 bug 的全部难点：**点不动和 App 坏了长得一模一样**，而 App 坏了还能重装，点不动只能猜。

这个 bug 其实是两条设计叠出来的：

1. `FolderTile` 只有一个 `urlString`。中转路线要的正是它（`weixin://` 精确、`open(_:)` 直达），通用链接路线要的却是另一个 URL。
2. 编辑器把三个路线平铺给用户选，而其中「直接打开」对绝大多数 App 根本不成立——**选择器看起来像一个偏好设置，实际上是一个能不能用的判断**。

### 修法

`FolderTile` 现在带两个 URL，由路线决定用哪个：

```swift
public var launchURL: URL? {
    switch strategy {
    case .universalLink: universalLink
    case .bounce, .systemShortcut: url
    }
}
```

关键的一点是 **`universalLink` 为 nil 时返回 nil，绝不回退到 `url`**。回退是最容易写、也最错的一版：`OpenURLIntent` 会忽略自定义 scheme，于是图块看上去是活的、点下去没反应——正好是这个 bug 本身。

配套三件事：

- `KnownApp.universalLink` / `FolderTile.universalLinkString`：从目录带到图块上，跟着图块存盘。取目录是「存的时候存下来」而不是「画的时候去查」，因为图块和目录可能不一致（用户改过、目录后来才学到、或者条目已被删掉）——**图块上的值才是被打开的那个值**。
- `LibraryRepair`：每次 load 跑一遍，幂等地把坏状态修回来。回填链接（`catalogID` 找不到时退到「名字 + 完整 scheme 都唯一命中」，救的正是这个手加的地图），再修路线。它会覆盖用户存过的路线选择——这需要理由：那不是偏好，是一个在这个位置上确定无效的设置，而默默留着它正是 bug 的来源。
- 编辑器：`universalLink` 为 nil 时菜单里直接不出现「直接打开」；万一是坏状态，写明原因并给一个一键改成中转的按钮。

### 苹果自家 App 的通用链接：几乎没有

「直接打开」需要目标发布通用链接，所以对系统 App 最自然的想法是找它的 `https://` 孪生。iOS 27 上一个一个试了（判据是进程：`pgrep -f 'Maps.app/Maps'`）：

| App | URL | 落在 |
|---|---|---|
| 地图 | `https://maps.apple.com/?q=coffee` | 地图 |
| 地图 | `https://maps.apple.com/?ll=37.331,-122.031` | 地图 |
| 新闻 | `https://apple.news/` | 新闻 |
| 新闻 | `https://apple.news/ATestArticle123` | 新闻 |
| 音乐 | `https://music.apple.com/library` | Safari |
| 播客 | `https://podcasts.apple.com/` | Safari |
| 图书 | `https://books.apple.com/` | Safari |
| App Store | `https://apps.apple.com/cn` | Safari |
| 备忘录 | `https://www.icloud.com/notes/` | Safari |
| 日历 | `https://www.icloud.com/calendar/` | Safari |
| 提醒事项 | `https://www.icloud.com/reminders/` | Safari |
| 快捷指令 | `https://www.icloud.com/shortcuts/` | Safari |
| 照片 | `https://www.icloud.com/photos/` | Safari |
| 健康 | `https://www.icloud.com/health` | Safari |

规律不是「苹果不做通用链接」——App Store 和媒体类 App 做，而且是故意的：那些 URL 是**指向某个内容**的可分享链接，多数点它的人想要的本来就是网页。而是**通用链接指向内容，启动器要的是指向 App 的链接**。只有地图和新闻发布了后一种形状的。

两个顺带发现：

- **域名有没有 AASA 不算数。** `www.icloud.com` 的 `apple-app-site-association` 是有效 JSON，但只声明了 `/directory/person/*` 和 `/directory/group/*`，App 们想要的一个都没claim。`apple.news` 声明的是 `"paths": ["*"]`，所以任意路径都进新闻。**只能实测，不能从域名推。**
- **能进 App ≠ 干净地进 App。** `https://maps.apple.com/` 会打开地图，**但 Safari 还在后台跑着**；`?q=`、`?ll=`、`?t=` 这些空参数形式也一样。所以最后选的是 `https://maps.apple.com/?t=m`：`t` 是地图类型参数，`m` 正是它的默认值，等于什么都不改，也不落 Safari。

### 想过的另外两条路

- **`maps://` 走中转。** 能到地图，但要多一次 AppFolder 闪现。既然同设备上已经有一个无跳转的 `https://maps.apple.com/?t=m`，没理由退而求其次。这也顺带说明「直接打开」对系统 App 是有意义的——只要那个 App 恰好发布了这样的链接。
- **深链进具体屏幕。** 比如 `https://www.icloud.com/calendar/` 之类。放弃的原因不是不行，而是**不对**：桌面上点一个图标应该落在和点主屏图标一样的地方，而不是某个指定页面。深链很像通用链接，但在「启动器」这个语境里是另一件事。

## 小组件的「液态玻璃」到底由谁决定

用户反问：「为什么 device hub 模拟器里，是有液态玻璃的效果的」。**反问是对的**，我前面写的「模拟器不渲染 Liquid Glass」是错的，已经改掉。下面把两件事分开：结论没变，理由变了。

### 更正：模拟器渲染 Liquid Glass，而且渲染得出来

之前说「dock、搜索框全是平的」，是因为取样时把显示尺寸当成了图片尺寸（1206×2622 的截图按 1.31 倍缩放显示），坐标对不上，扫到的是旁边的壁纸。重测一遍，结论相反：

| 表面 | 测量 |
|---|---|
| dock | 它的亮度**逐列跟随它背后的壁纸**，跨 x 的相关系数 **r = +0.997**；壁纸亮度从 15.5 变到 67.0，dock 跟着从 38.0 变到 83.4 |
| dock 边缘 | 左边缘有一道比内部亮的**镜面高光**（x=32 处 L=12.6 的暗色，到 x=56 跳成 L=40.0），内部又是被压暗的透射 |
| 搜索胶囊 | 边缘一道亮边，内部透出壁纸的斜带 |

壁纸被透射、边缘有镜头式的亮边和弯曲——这就是玻璃，模拟器在做。用户接着指出的第二条更直接：**把两个 App 拖成一个文件夹，那个文件夹也是玻璃的**，实测它内部透出的就是它背后的壁纸（`#967060` / `#9D7762`，跟着壁纸走）。两条都指向同一件事：玻璃管线在这台模拟器上跑着，而且跑在**两种**宿主表面（dock、文件夹）上。

### 结论没变：App 画不出一个透明的 widget

在 widget 里，**画什么都进不去壁纸**。同一块 widget、同一张 `#B59989` 的棕色壁纸、同一个浅色模式，四种写法：

| `containerBackground` | 渲染出来 | 吃到壁纸了吗 |
|---|---|---|
| 纯红 | `#FF4A4D` | 不适用——但说明这个钩子是生效的 |
| `Color.black.opacity(0.45)` | `#969696` | **没有**。纯中性灰，R=G=B |
| `.ultraThinMaterial` | `#F4F4F5` | 没有，纯色 |
| `.glassEffect(.regular, in:)`（iOS 26 真 API） | `#FCFCFC` | 没有，纯色 |

第二行是决定性的。45% 的黑如果和那张壁纸合成，应该是 `#64544B`；实际是 `#969696`——**黑是被合成到白色上的**，不是壁纸。也就是说 widget 的快照底下有一层不透明的白，拿不到壁纸。material 和 `glassEffect` 退化成纯色是同一个原因。

顺带发现：那张 `#B59989` 的棕色壁纸，和上面那张里挂件底下的壁纸，正好**不是同一张**。同一台机器、同一个模拟器、同一个浅色模式，换个壁纸结论就要重测——所以这条结论是「在白色板子上」，不是「在所有壁纸上」，记下来免得下次误用。

### 那玻璃从哪来

来自**桌面的「图标外观」**（长按桌面 → 编辑 → 自定，四档：默认/浅色/深色/透明，另有自定+色调）。四档都在替系统决定**它自己画的那块板**是什么：默认跟浅色/深色走，透明档最透。**这件事 App 不参与**——同一份 widget 内容在四档下都是同一份内容，我们能选的只是「画不画自己那块板」。所以「默认档算不算玻璃」不是 App 能选的档位，是这一档下系统画什么的问题；模拟器上量到的是不透明白板（见「默认档那一格，模拟器答不了」），真机上待验。

用户的要求是：「**我要的是不开全局透明的情况下支持透明**」。所以这里必须把两件事分清楚，它们不是一回事：

| 那个开关是什么 | 作用范围 | App 能不能读到、能不能改 |
|---|---|---|
| **全局的**图标外观（桌面 → 编辑 → 自定） | 整台设备的桌面 | 不能 |

**一个只对我们这个 widget 生效的「透明」开关不在 iOS 上存在。** 找过一遍，能拿到的最接近的东西是 `_preferredSystemWidgetBackgroundStyle`（chronod 里一条 `%{public}s Setting _preferredSystemWidgetBackgroundStyle to: %{public}ld` 的日志，配一个 `Setting widget style to clear: %@`），但它的名字和主机进程都说明它是**系统级**的、由系统写的，不是给 App 用的 API——SDK 里没有任何公开入口能设它。**没找到 per-widget 的透明开关，不编。**

App 侧能做的就这两行：

```swift
.containerBackground(for: .widget) { Color.clear }   // 我不画
.containerBackgroundRemovable(true)                  // 允许系统把底板撤掉
```

第二行是**前提**，不是开关本身：它向系统声明「我的版式不是围着底板设计的」，于是**那些偏好无底板的场合**（用户切到透明是其中一种）才有权把底板撤掉。SDK 自己的措辞（`WidgetKit.swiftdoc` 里摘的）比头文件清楚：

> In most cases, mark the background container of a widget as removable to allow people to place the widget in as many contexts as possible.
> If you mark a background as nonremovable, the system always displays the background container of the widget. Note that the background may render differently; for example, it can appear faded or desaturated.

「非 removable 就永远显示底板」——反过来读，removable 是撤掉底板的必要条件。但**撤不撤是系统按上下文决定的**，App 没得选。所以：**系统级的「透明」App 改不了；App 能做的只是把自己准备好，让系统想给的时候给得出来。** 超出这一步的任何承诺都是编的。

顺带清掉一个一直挂着的待办：`supportedMountingStyles` 的文档明说「The mounting style view modifier only has an effect to widgets in visionOS」，所以那条 iOS 26 的 `WidgetMountingStyle` 在 iPhone 上不起作用，不用再试。另外 `widgetTexture(_:)` 的文档写着「By default, all widgets use the `glass` widget texture」，而它是 visionOS-only（iOS 标了 unavailable）——也就是说在材质这件事上，我们的 widget 平台的默认值本来就是玻璃，只是 iOS 不给我们调它。

### 为什么 widget 里画不出玻璃（真原因）

不是因为模拟器没有玻璃管线——它明明有。真原因是 **widget 不是内部贴玻璃，而是整体被重新挂载**：

系统把 widget 的内容渲染到一块**不透明的白板**上，然后再把这块白板当作一个整体，按当前的「图标外观」贴到桌面上。玻璃发生在**贴上去那一步**，由系统画；widget 里画的任何东西都已经在板子上了，碰不到壁纸。

正面证据：**系统自己的 widget 也是白板**。地图组件和日历组件的内部都是纯 `#FFFFFF`，边缘干净利落（`#4B3427` → `#FFFFFF`，没有半透明过渡），而且**壁纸在组件底下是被完全挡住的**——同一张壁纸，组件外的边界是硬边。系统组件都没有内部玻璃，第三方组件当然更没有。

反过来说：如果哪天系统让 `containerBackground` 真的透出壁纸，那只能是它把板子换成玻璃再贴——仍然是系统那一侧的事。

这台机器没有 Simulator.app（Xcode 27 换成 DeviceHub.app），`AXIsProcessTrusted()` 为 `false`，`osascript` 的 `click at` 报 -25200，所以没法自己点进「编辑 → 自定」去切那一档。找过那个设置在哪儿持久化：`com.apple.springboard.plist` 里没有、`com.apple.chronod.plist` 里没有（只有 `extensionsPendingDescriptorRefetch` 这类）、`com.apple.PosterBoard.unprotectedUserDefaults.plist` 里也没有、`HomeScreenSettings.bundle` 没有、逐字节扫过设备上所有偏好 plist 也没有。SpringBoard 二进制里只有一个 `com.apple.springboard.homeScreenIconStyle`，但那是 **XPC entitlement**、不是偏好键；字符串表里对应的是 `STYLE_PICKER_TITLE` / `UNDO_CHANGE_ICON_STYLE`。

这次把模拟器运行时的共享缓存（`dyld_sim_shared_cache_arm64`）按 `*IconStyle*` 形状扫了一遍，拿到一批符号名，最有信息量的是这几个：`sbh_homeScreenIconStyleConfigurationInferringIfNecessary`、`noteIconStylePickerDidDismiss`、`updateAfterIconStyleTraitChange`、`SBHIconStylePreviewManager`、`iconViewsToPreviewForIconStylePicker`。它们说明两件事：IconStyle 是当作一个 **trait** 往下发的（不是读一个用户默认值），而选择器**只在动作里写它**（`didChangeIconStyleWithColorPicker` / `setIconStyle` 都是 setter）。**那时候仍然没找到持久化键**——后来找到了它在哪：poster 系统里，见「默认档那一格，模拟器答不了」第二节。它不是一条 `defaults` 键。

### 所以现在是什么样

浅色下是系统给的白色底板（`#FFFFFF`，不透明），深色下 `#19192A`——跟着外观走，确实是块材质。**玻璃是系统在这一层画的，App 换不来**：能改的只有「画不画自己那块板」（`跟随系统` = 不画，把这一层让给系统）。

### 2026-09-27 补测：`.widget` placement 上也试过了，结论不变

前面那次结论有个漏洞：45% 黑是画在**内容**里的，不是画在 `containerBackground` 那个 placement 上。而 `ContainerBackgroundPlacement.widget` 的文档原文说的是 "the container that is **under the widget**"——也就是「组件底下那块板子」。用户要的是这一层，所以这一层必须单独测。

这次模拟器上**桌面真的有我们的组件**（`IconState.plist` 第 0 页里就有 `widgetIdentifier = 'AppFolderWidget'`，中号），所以能直接量。写了临时探针 widget 放进 bundle，三种写法各测一轮：

| 写法 | 读数 |
|---|---|
| 内容里的 50% 红 | `#FD9A9C` |
| 内容里的 100% 白 | `#FEFEFE` |
| 内容里的 100% 红 | `#FC3E42` |

内容层：三块全都**精确落在白板上**（白→`#FEFEFE`，红→`#FC3E42`，50% 红→白与红的中点），和背后壁纸毫无关系。

**placement 层**：`containerBackground(for: .widget) { Color.red.opacity(0.5) }`，把中号组件放在桌面顶部，让同一块板子横跨壁纸的亮区和暗区——

| 位置 | 读数 |
|---|---|
| 板内 9 个采样点 | `#FFA8A9 … #FFA8A9`（**全同**） |
| 同一高度板外壁纸 | 左 `#745131`、右 `#E7E2DE`（**差 3 倍亮度**） |

板内跨了壁纸从 `#745131` 到 `#E7E2DE` 的范围，读数**一个字节都不动**。

**结论**：这个 placement 不是「壁纸的合成层」，而是「选中一块不透明的底，再把内容画上去」。板子是系统选的——浅色给白、深色给 `#19192A`、用户切到玻璃档给玻璃——但**App 往里放什么，它都不会透**。

`.regularMaterial` 放进 placement 也一样：渲染成一块纯白 `#F6F7F7`，不透明。

**`glassEffect` 也放进 placement 试了**（`.regular` 和 `.clear` 两档，各占一个中号 widget，板子横跨壁纸从 `#A6743E` 到 `#493F38`、从 `#C3B3A2` 到 `#E6E1DC`）：两块板子都是**纯 `#FFFFFF`**，横向纵向各七个采样点零变化。

**那条路到此为止是封闭的**：内容层试过 4 种（纯色 / 半透明色 / material / glassEffect），placement 层试过 3 种（半透明色 / material / glassEffect×2），**七种写法，没有一种能让壁纸透上来**。板子始终是系统画的那一块——所以「让系统画」（`跟随系统`）是唯一能碰到它的姿势，而系统画成什么由用户的图标外观决定，不由 App。

> ### 那 WidgetLoft 的「Liquid Glass」到底是怎么来的
>
> 这是用户反复追问的问题（"为什么widgetloft可以"），答案在先看它的证据、再自己实测之后才清楚：
>
> **写这一节的时候我给过一个太满的结论，用户当场纠正了，记在这里：** 原话是「它的透明就是用户那颗『图标外观』开关」，潜台词是**默认档不是玻璃、想玻璃得自己去切**。用户的原话是「我选择的就是默认而不是透明主题，然后也是液态玻璃的啊」——**默认档本来就是玻璃**，不需要切任何东西，也不需要裁壁纸。下面是把两边的证据重新摊平之后的样子。
>
> **能确认的部分：** 板子是**系统**画的，App 侧只决定「画不画」。这件事两侧都成立——我们做的 `AppFolderWidget` 在同一个模拟器、同一张壁纸上是纯 `#FFFFFF`，系统给的那块板；WidgetLoft 在它的截图里是纯 `#1C1C1E`，也是系统给的那块板。**App 侧没有任何可差别的空间**，所以「它做得到、我们做不到」这个问法是错的。
>
> **两边的差别只在「让系统画的板」和「自己盖上去的板」之间选哪个。** 我们三种档位里的「跟随系统」= 让系统画，和它营销页里的 Style `Transparent` 是同一件事；「纯色 / 渐变」= 自己盖。按这个对齐，它宣传的 glass 档**我们已经有了**，缺的只是文案和引导——之前 App 里一个字都没写。
>
> **它的证据撑不起「真透」这一半。** `05_glass.png` 板内一片恒定 `#1C1C1E`，横跨背后壁纸从粉到青的全部变化，**一个字节都不变**——那是不透明深色板 + 玻璃描边，不是透出壁纸。而且那张图整体是一张营销渲染（两块圆角板带投影浮在渐变色块上，外面还套了一圈深色边框），不是设备截图，**不能用来证明它在真机上透不透**。
>
> **所以真正的未知只剩一条，而它在模拟器上答不了：** 真机默认档下，系统给 widget 画的那块板会不会跟着壁纸走。见下面「默认档那一格，模拟器答不了」。

> 顺带记两条这轮踩到的坑，都不是代码问题：
> 1. **widget extension 的 Info.plist 不能声明 `NSExtensionPrincipalClass`。** 加第二个 widget 时顺手加上去试了，结果 `simctl install` 直接失败，报的是一句「无法安装」+「请稍后再试」，真正的原因埋在 `Underlying error` 里：*defines either an NSExtensionMainStoryboard or NSExtensionPrincipalClass key, which is not allowed for the extension point com.apple.widgetkit-extension*。**加第二个 widget 根本不需要这个键**——`@main WidgetBundle` 加一行就行。
> 2. **探针要能被量到，就不能有别的东西盖在上面。** 第一版探针涂了四块色，第二版换材质时忘了改内容，彩色残留把那块板子整体盖住，量出来的是「板子 + 彩色层」的合成值，读数全是误导。改成一个角标之后才量到干净的数字。
> 3. **探针 widget 不能全靠传参。** `Widget` 协议要求一个 `init()`，用 `let` 属性 + 逐字段构造函数是编不过的；属性给默认值才两者兼得。另外 `Glass` 是 iOS 26 类型，`Widget.body` 却要对最低版本可见，所以玻璃得在 `body` 里用 `if #available` 现造，不能当参数存。

## 做「小组件外观」时翻出来的三件事

这一节是照着 WidgetLoft 补外观档位时量出来的。三条都不是新 API，是**旧 API 的位置放错了**。

### 一、能画颜色，但画错了一层

外观要做的第一件事是「纯色档」：用户选一个颜色，组件就铺这个颜色。顺理成章的写法是放进 `containerBackground`——那是上面第七次实验里唯一能让填充落地的 hook。

铺 `#3478F6`，量出来是 **`#4583F7`**：比选的颜色淡了一截，而且是**有方向地淡**。

| 位置（组件内 y，像素） | `containerBackground` 里的读数 |
|---|---|
| 1500（组件顶边） | `#4D88F7` |
| 1600 | `#4A86F7` |
| 1730（中线） | `#4583F7` |
| 1850 | `#4180F7` |
| 1930（组件底边） | `#3E7FF7` |

拿 `#3478F6` 反推「掺了多少白」：顶边 +12%，中线 +8%，底边 +5%。**这是一层压在我们上面的白纱，从上往下渐薄。**

同一份 `#3478F6` 改画在**内容层**（`.background`）——同一台模拟器、同一张壁纸、同一个组件，只有画的层换了：

| 位置 | `containerBackground` | 内容层 | 差 |
|---|---|---|---|
| 1500 | `#4D88F7` | `#4D88F7` | 0 —— 还在圆角外侧 |
| 1600 | `#4A86F7` | **`#3478F6`** | +11% 白 |
| 1730 | `#4583F7` | **`#3478F6`** | +8% |
| 1930 | `#3E7FF7` | `#3E7FF7` | 0 —— 白纱已经褪尽 |

**结论：widget 的内容层在系统那块玻璃板之上。** 板子在下面（`containerBackground` 那层），玻璃是系统在它上面合成的，而内容层又压在玻璃上面——所以内容层画什么就是什么，一个字节都不偏。

这条同时解释了两件事：一是为什么之前的实验里往 `containerBackground` 里塞什么都「不透」——那不透明的白纱正是系统的玻璃；二是**为什么这次能承诺「纯色」**：我们不是在跟那块板子打架，是盖住了它。

顺带量到一件事：**系统会把内容裁到组件的形状**（圆角 83 px = 27.7 pt）。两条路的圆角内缩读数完全一样（顶行 96 px，往下 80 px 处 1 px），所以铺满的色块不需要自己写圆角。

### 二、四周那 18 pt 是系统的，不是我们的

内容层能铺色之后立刻冒出第二个问题：色块**铺不满**。组件 349.7 pt 宽，色块只有 313.7 pt，四周各留 18 pt 是白的。

那不是边距算错，是系统的 **content margins**——`contentMarginsDisabled()` 就是那个开关。关掉之后色块铺满 349.7 × 164.3 pt，和组件严丝合缝。

关掉的代价是网格要自己让出这 18 pt。让法不是写死 18，而是读 `\.widgetContentMargins`——系统本来要用的值——再 `padding` 回去。这样同一个 `FolderGridMetrics` 在两种内容边距下算出的图标位置是一致的，也就顺带堵上了编辑器预览和桌面组件之间那 18 pt 的偏差。

### 三、量这套东西，得先把「什么时候重画」搞对

这轮最费时间的不是代码，是**截图截早了**：

1. **改 `library.json` 不会让桌面重画。** 得让 App 跑一次（`LibraryModel.persist()` 里的 `reloadAllTimelines()`），而 App 启动后要等安装探测跑完（`lastProbeAt` 变化）才写完这一次。**等这个字段变了再截图**，否则量到的是上一轮的设置——一开始量「黑色纯色」量出 `#827270`，就是这个原因。
2. **启动过 App 之后，桌面翻到的是 App 图标那一页。** 组件在第 0 页，启动 App 后系统停在有 AppFolder 图标的那页，截到的是空桌面。**`simctl shutdown` + `boot` 才能把桌面摆回第 0 页**——顺带也满足重画。

这两条合起来就是 `/tmp/measure.sh`：写文件 → 启动 App → 等 `lastProbeAt` 变 → 杀 App → 重启模拟器 → 截图。跑一轮约 40 秒，比反复试错快得多。

**这套办法只验得了 App 侧画的东西**，验不了「玻璃档下系统画什么」——那个仍然要点进「编辑 → 自定」，见第五节。

### 一、模拟器确实在渲染玻璃——只是不给 widget 画

### 二、那个菜单找不到，但不是没找

要把这一格补上，唯一的路是把「编辑 → 自定」里的图标外观切到玻璃档再量一次。这一轮把它的存储位置扒到底了：

- `xcrun simctl ui` 只能改 light/dark，没有图标外观；`simctl spawn` 在这台机器上坏了（`LaunchdSimError 111`）。
- `com.apple.springboard.plist` 里**没有**这个键；把设备 `Library/Preferences` 下每个 plist 扫一遍也没有。
- SpringBoard 二进制里那个 `com.apple.springboard.homeScreenIconStyle` **不是偏好键**，它和 `application-removability.proxy`、`opensensitiveurl` 并列在一个 `<key>…</key><true/>` 块里，是 SpringBoard 暴露的 **mach service 白名单**。
- 真正的家在 **poster 系统**里：`PosterBoard.framework` 里有 `homeScreenIconStyleVariant`、`NPRPosterHomeScreenConfigurationAppearanceType`、`posterUpdateUserSelectedHomeScreenIconStyleVariantsForTypes:`、`PRPosterContentStyleGlassAppearanceSupporting`、`applyGlassIfDesiredToView:forIconImageAppearance:sourceView:`——图标外观是 Home Screen poster 配置的一部分。配置存档在 `Library/Application Support/PRBPosterExtensionDataStore/<n>/PBFPosterExtensionDataStoreSQLiteDatabase.sqlite3`，但这台模拟器上 `poster` 表只有 8 行、角色只有 `PRPosterRoleLockScreen` 和 `PRPosterRoleAmbient`，**没有任何 Home Screen 外观变体**——因为从没被改过，默认值不落盘。

结论：**在模拟器上改不了这一格**，不是因为没找到开关名，是因为它压根没有「默认值以外」的存储位置可写，而写入它的 UI 需要点进 SpringBoard 的编辑态。

### 三、所以这一格只能留给真机

已量到的和未量到的，界线画在这里：

- **已量到**：App 侧没有可差别的空间。系统给 widget 的板子，App 换七种写法都碰不到（夹在 `containerBackground` 的玻璃下面），内容层画的颜色则**原样**渲染——所以我们能承诺纯色和渐变。
- **已量到**：WidgetLoft 的 "Liquid Glass, really see-through" 那张图是营销渲染，板内恒定 `#1C1C1E`，不透。
- **未量到**：真机默认档下，系统给 widget 画的那块板会不会跟着壁纸走。**模拟器说不会，用户说会**，两边都没法在这里判谁对。

`跟随系统` 这一档现在的做法（不画，全交给系统）在两种可能下都是对的：真机默认档是玻璃，它就跟着玻璃；不是，它也和我们以前一模一样。**App 侧不需要为这一格改任何代码**，需要改的是别再把「切到透明档」写成前提。

### 2026-09-29 更正：WidgetLoft 的组件是真透的，上面那一节写错了

上面这一节下过一个太满的结论：「App 侧没有可改的，玻璃那一层在系统手里」。**这一句被真机测量推翻了。**

用户的原话是「为什么widgetloft可以呢，我确实安装了，而且有液态玻璃效果」，我把它当真机上的对照测了一遍。设备是 Nate's iPhone（iPhone 18 Pro Max / iOS 27.0），在 `devicectl device capture screenshot` 下连拍两帧，中间只翻了一页：

- `light1.png`（1:22）——WidgetLoft 的两个组在这页
- `hs_now.png`（1:33）——我们的组在这页

**这两帧是同一张壁纸、同一个滚动位置。** 底部空白带（x 200–1120、y 2440–2560，1278 个采样点）**逐字节相同，最大差 0**。所以对任一像素，一帧里有板子、另一帧里就是**没有任何遮挡的裸壁纸**——比「拿板子旁边的壁纸当参考」干净得多（后者会被板子自己的边缘高光污染，见下）。

**判据**：`板内像素 = gain × 同一像素的裸壁纸 + offset`，**逐像素配对**。板子的边缘、圆角、描边全部排除在外，只取纯板面。

| 表面 | 取样区 | gain | r | r² |
|---|---|---|---|---|
| WidgetLoft 的板 | 905,1790 起 315×315，空板 | 0.430 | **+0.901** | **0.812** |
| 　同上，对壁纸先做 σ=4 模糊 | | 0.612 | **+0.988** | 0.975 |
| 我们的板 | 1010,1250 起 205×200，空板 | −0.004 | −0.042 | 0.002 |

**WidgetLoft 那块板是壁纸的模糊副本。** 最佳模糊半径 σ≈4 px（在 1320×2868 的截图上，即约 1.3 pt），逐像素 r=0.988、r²=0.975；gain 0.612、offset +40 把它压在原来亮度的一半上下——一层半透的模糊。我们的板同一测法 gain ≈ 0、r ≈ 0：**一点关系都没有。**

**独立佐证（不依赖回归）——壁纸的亮脊穿过了板子。**

同一条 y 上，壁纸最亮那道脊的「峰值减基线」是：

| y | 裸壁纸 | σ=4 模糊后 | σ=6 模糊后 | σ=8 模糊后 | ★ WidgetLoft 板内 |
|---|---|---|---|---|---|
| 1970 | 113 | 62 | 47 | 37 | **41** |
| 2000 | 118 | 66 | 50 | 41 | **44** |
| 2030 | 126 | 72 | 56 | 46 | **49** |

**板内残留的脊高（41–49）正好等于壁纸做 σ=5–6 模糊之后的脊高（47–56）。** 板子自己画不出这条随 y 一路变化的脊；它只能来自壁纸。这一步不依赖任何拟合，是把模糊半径钉死在 4–6 px 的那一脚。

反过来说，**上一版用的那条「亮脊」推理是错的**：当时说「脊在板外 x≈88、进板后出现在 x=250–300」，可那是在**两张不同截图上**比 x 位置——换页之后壁纸是同一张，但两个盒子在页面上的位置不同，板的左边界差了 600 px，脊的位置自然也对不上。那一步的结论碰巧是对的，推理是无效的，这里换成了同 x 的测法。

**我们的和 Apple 的都不是**：我们的板 gain −0.004、r −0.042——板内亮度 151–255 而同一像素的裸壁纸 0–255，两者毫无关系（我们的板里那点变化是系统白纱的渐变）。Apple 天气组件同样是一块恒定深色板。

**这条更正意味着什么**：之前「widget 做不了玻璃，连 Apple 自己的组件都不是」的结论，说的是 **Apple 自己的组件**，不是第三方组件。第三方能做到。用户的判断是对的，这一节原来那些字是错的。

**试过并且失败的（都在真机上，量过，都是平的）**：

| 试的东西 | 结果 |
|---|---|
| `.containerBackgroundRemovable(false)` | 和 true **逐字节相同**，max delta 0 |
| widget Info.plist 的 `PreferredSystemWidgetBackgroundStyle = 2` | 平的 |
| 系统 Liquid Glass 档位 0.0 / 0.5 / 1.0 | Dock 和搜索框跟着变，**组件板子一个字节不变** |
| `containerBackground` 里的浅色 / 深色 | 相同 |
| 它的 `05_glass.png` 商店图 | 恒定 `(28,28,30)`，是营销渲染，不能当证据 |

`WidgetTexture.glass` / `widgetTexture(_:)` 在 27.0 SDK 里仍然是 `@available(iOS, unavailable)`。

### 那道玻璃在 SDK 里叫 `WidgetBackgroundStyle`，但没给第三方

翻 27.0 SDK 时找到了这一整套东西，**它们就是「一块板子怎么画」的旋钮**：

在 `WidgetKit.framework/WidgetKit.tbd` 的导出表里（Swift 修饰名，`swift-demangle` 解出来的原文）：

```
SwiftUI.WidgetConfiguration.backgroundStyle(WidgetKit.WidgetBackgroundStyle) -> some WidgetConfiguration
SwiftUI.WidgetConfiguration.isTransparent(Swift.Bool) -> some WidgetConfiguration
SwiftUI.WidgetConfiguration.supportsAccentedContent() -> some WidgetConfiguration
SwiftUI.WidgetConfiguration.supportsVibrantContent(Swift.Bool) -> some WidgetConfiguration
SwiftUI.WidgetConfiguration.enableContentMarginsForFirstParty(Swift.Bool) -> some WidgetConfiguration
```

在 `ChronoServices` 的二进制里：类型 `CHSGlassOptions`，字段 `style` / `fraction` / `primaryColor` / `secondaryColor` / `filterStyle` / `primaryTintColor` / `secondaryTintColor` / `accentedAlternateBackground` / `accentedDesaturatedMode`，外加 `wantsSubduedGlass`、`wantsWhitePointBoost`、`_glassM44`（一个 4×4 颜色矩阵）、`UseAlternateGlassColorMatrix`。`style` 的取值串是：`glassClearLight` / `glassClearDark` / `glassAccentedLight` / `glassAccentedDark` / `solariumColorized` / `transparentDesaturated` / `accented` / `unknown`。

在 `SpringBoardHome` 里：`SBIconWidgetGlass`、`_appropriateWidgetRenderScheme`、`_appropriateWidgetTintParameters`、`_appropriateColorFilter` 一组私有属性，紧挨着 `_backgroundType`，而它的取值串就两个：**`gradient` / `glass`**。同一个类里还有 `SBIconWidget` / `SBIconWidgetGlass` 这一对相邻的 type name。

**但这四个 `WidgetConfiguration` 方法，`.swiftinterface` 里一个都没有**，SwiftUI 文档里也没有。对照同一个 tbd 里的 `containerBackgroundRemovable()`——它同样不在 `.swiftinterface` 里，却在 `.swiftdoc` 中有文档、在 `developer.apple.com` 上有页面。差别的来源是：**`backgroundStyle(_:)` 没有 `@available` 标注。** 一个 Swift 调用点无法在「部署目标 18」的前提下安全地引用它，链接器也不给。

所以结论是：**Apple 有这道玻璃，有整套调它的参数，第三方一行都调不到。** WidgetLoft 拿到它，只能是它比我们多了一样东西——最可能是登录进 App Store 之后由 App Store Connect / `CHSWidgetDescriptor` 下发的 `supportsAccentedContent` / `supportsVibrantContent`（这两个是**描述符**上的字段，能编译期以外地打开），而我们的描述符是 `devicectl install` 装上去的，走不到那条路。

> 顺带把上一版的两条记录作废：① 说 WidgetLoft 的板子上「盖着翻页圆点」（x≈1100–1120、y≈1520）——放大看那个位置只有主屏上 `X` 那个 App 的图标，没有圆点。② 说「还没试 `sbh_applyWidgetGlassWithTintColor:...`」——那串符号在这次 dump 出来的 SpringBoardHome 里根本不存在，是我从别处照抄的，不成立。

### 2026-09-29 模拟器实测：把描述符里那一位改成 2，板子真的变成了玻璃

上面那句「第三方一行都调不到」到此为止只在**编译期**成立。绕开编译期，这个旋钮是能动的——它躺在 `chronod` 的缓存里，一位整数。

**做了什么。** 模拟器上 `~/Library/Developer/CoreSimulator/Devices/F022B294-…/data/Library/chronod/chrono.sql`，表 `Descriptors`，一行是我们的扩展。它的 `data` 是一份 `NSKeyedArchiver` 二进制 plist，根 `CHSWidgetDescriptor` 在 `$objects[2]`，其中 `backgroundStyle` 是**普通 int**（不是 UID 引用）：我们的 = **0**，`BatteriesAvocadoWidgetExtension` 和 `PeopleWidget-iOS` = **2**。改这一位、写回、重启模拟器。**App 本身一行没动，数据库改前已备份**（`chrono.sql.bak-before-bgstyle`）。

**改前的板子**是纯白：`(255,255,255)` / `(239,239,240)`，没有任何壁纸成分。

**改后的板子**——用同一套「同坐标配对回归」，抠掉圆角边缘，x 110–1100 / y 1520–1950：

| 参照 | 增益 | r | r² |
|---|---|---|---|
| 裸壁纸（同坐标） | +0.613 | +0.939 | 0.883 |
| 裸壁纸 σ=4 模糊 | +0.670 | +0.970 | **0.940** |
| 裸壁纸 σ=5 模糊 | +0.676 | **+0.971** | 0.942 |

拿真机上量 WidgetLoft 的同一套方法对齐：它对着裸壁纸是 **0.430 / +0.901**，对着 σ=4 模糊是 **0.612 / +0.988**。**我们改完这一位之后，量出来的东西和它落在同一格上**——一块壁纸的模糊拷贝，增益约 0.6、再叠一个约 +32 的偏移。

**一条差点写错的判据。** 之前记的「板外的亮脊延伸到板内」是**假的**：那条亮脊在 x≈100–110，而板子左边界在 x≈79——它本来就在板**外面**。换成整行找最亮的 x 之后真相反过来了：裸壁纸上这条脊从 y=1500 的 x=951 一路走到 y=1950 的 x=800（一条斜线），而在玻璃帧上，x 951/884/842 这些位置全都落在板子**里面**，整行最亮点反而是 x=1204 的板外背景。也就是说那几行里，**板内**（x≈900 一带）比板外更亮——和「板子把壁纸整片接了过来」一致。

**一处不是透射的成分，记下来免得以后误读。** 板内每一行的均值相对裸壁纸有个自上而下的斜坡：y=1480 时 −16.0，y=1920 时 −0.2，y=1960 翻正到 +12.2。这是玻璃自己的顶边缘高光/暗边，在旧的白板上当然没有。

**所以那道玻璃是什么，现在从「有名字」变成了「有名字、有地址、改一下就能看」。** 但这一条同样要说清楚：**这是在模拟器里由我手改描述符缓存做出来的，不是任何一次构建能做出来的，也还没在真机上验证过。** 真机上 Nate 的 iPhone 有一份同样的描述符，但 `devicectl` 读不了第三方容器，那条路是断的。App 这一侧的状态因此**没有任何变化**：`透明` 仍然是 App 能碰到那道玻璃的唯一姿势。

### 2026-09-29 真机这一轮：装上了，玻璃没跟过来（预期之内）

用户要求「给真机也装一下看看」。做了三件事，结论一句话：**真机上的 App 是新的，板子还是白的**——因为让描述符变成玻璃的那一位在真机上够不着。

**一、真机链路本身是通的。** `xcodebuild -destination 'platform=iOS,id=00008160-…'` 构建成功，`devicectl device install app` 把新的 `AppFolder.app`（含 `PlugIns/AppFolderWidget.appex`）装进了 `private/var/containers/Bundle/Application/BE8B1FFC-…/`，`info apps` 能列到 1.0 (1)。签名没挡路。

**二、真机上够不着那一位，而且不是「权限不够」这么简单。** 逐条试过：

| 试的 | 结果 |
|---|---|
| `copy from --domain-type appDataContainer`（我们的 app） | 能列出（`Documents`/`Library`/`tmp`），也能读——**但那只给我们的容器** |
| 同一条命令、Apple 的 bundle | `ContainerLookupErrorDomain error 2` |
| 我们的**扩展**容器（`…appfolder.widget`） | 能列出，**同样只是我们自己的** |
| `../..` 往上走 | `StreamingAction` 报错，出不去 |
| `sysdiagnose --destination` | `CoreDeviceCLISupport.DiagnoseError error 0`，没产出 |
| `info mountpoint` 给的 `DeviceFS` 挂载点 | 只有 `AppDataContainers/`、`AppGroupContainers/`、`DiagnosticReports/` 三个空壳目录，没有 `chronod` |

顺带纠正两件早先说错、或容易想错的事：

1. **`devicectl` 读写我们的容器一直是好的**，之前记的「读不了第三方容器」只对 Apple 的 bundle 成立。**但这没有用**：`chronod` 的库不在任何 app 容器里，它在系统分区。往 App Group 里写文件改不了 SpringBoard 或 chronod 怎么想。
2. **「往 App Group 里塞一个 plist 就行」是没出处的猜测。** 这个键的名字后来确实找到了（见下），但它**不在任何 Info.plist 里、也不在描述符里**——上真机拿它去赌，是拿一个还没验证过的东西赌真机上每一步都要用户手动确认的代价。

**三、换了个更有意思的问法：Apple 凭什么把 2 给这两个扩展。** 在模拟器里克隆了一台干净设备做对照（`simctl create` + 把描述符库里 Apple 那两个扩展的值都归零后开机），结果是：**`BatteriesAvocadoWidgetExtension` 开机后自己又变回了 2**，另两个是 0。也就是说这不是安装时烧进去就不动的常量，而是**每台设备现场决定的**——同版本同二进制，不同设备给不同值。

然后把它和同目录里 `BatteriesWidgetExtension.appex`（值 0）对比：两个扩展的 Info.plist 键几乎一模一样（`NSWidgetBackgroundColorName` 一个 `WidgetBackground` 一个 `WidgetBackgroundColor`），`nm -u` 的导入表里只有 `_NSExtensionMain` 和 `$s9WidgetKit16TimelineProviderP` 两个符号，**没有任何一个 `backgroundStyle` / `WidgetBackgroundStyle` / `glass` 字样**。所以在 Apple 自己这两个扩展之间，**找不到一个「凭什么给 2 而不给 0」的开关**：不在 Info.plist 里，也不在二进制引用的符号里。

**四、把模拟器的 dyld 共享缓存扒了一遍，那个「未知的键」有名字了。** 缓存里（`dyld_sim_shared_cache_arm64`，2 GB）能直接 grep 到这些字符串：

```
PreferredSystemWidgetBackgroundStyle            ← 一个 UserDefaults / plist 键名
WidgetPreferredSystemBackgroundStyleEnvironmentKey
PreferredSystemWidgetBackgroundStyleKey
com.apple.widgetkit-extension
```

以及**一份硬编码的 bundle id 列表**，就在同一个字符串区、紧挨着上面那个键（偏移 177,973,076 起），前后是 `com.apple.AppStore.Widgets`、`com.apple.Batteries.BatteriesAvocadoWidgetExtension`、`com.apple.PeopleViewService.PeopleWidget-iOS`、`com.apple.mobilecal.CalendarWidgetExtension` …… 一直排到 `com.apple.tips.Widget`，**四十来个，全是 Apple 自己的**。同区的 feature flag 串里还有一个 `GlassPrototype`。

把它和前面量到的对照，四件事就能拼成一句话：

| 观察 | 说明 |
|---|---|
| `BatteriesAvocadoWidgetExtension` 是 2，`BatteriesWidget` 是 0 | 两个都是 Apple 的，都在那份列表里 |
| Apple 的 `CalendarWidgetExtension` / `Maps` / `News` / `Photos` 也是 **0** | **进了列表 ≠ 给玻璃** |
| 那份列表里没有任何第三方 bundle id | 列表是**方向**（哪些扩展配得上玻璃），不是**判据** |
| 真机上 WidgetLoft 的板子是玻璃，而它不在列表里 | 所以列表之外还有一条路，判据是**每台设备现场算的** |

也就是说「凭什么给 2」不是某个 Info.plist 布尔值，而是一个**看扩展身份的运行时策略**；而 `PreferredSystemWidgetBackgroundStyle` 那个键名摆在那里，说明这条策略**还有一个人工/默认覆写口**。哪个是真的、怎么用——**只有真机上 WidgetLoft 的描述符能定案**，那一个文件就能分辨「它走的是 Apple 内部那条路」还是「存在一个第三方能拿到的键」。

**这一段想说的结论：** 那条路我走不到，是因为**缺少一个还不知道是什么的键**，不是因为它不存在——Apple 的 `BatteriesAvocadoWidgetExtension` 每次开机都能拿到 2。而要说清楚那个键是什么，需要的正是**真机上 WidgetLoft 的描述符**（一个已经进 App Store、板上真的是玻璃的第三方扩展）。那个文件在系统分区里，`devicectl`、备份、容器复制三条路都到不了；能到的是 **Xcode 的 Devices and Simulators 窗口里「Download Container」**——它有一条 `devicectl` 没有的容器列表通道。这一步要人在 Xcode 上点两下，我不替用户做主，所以停在这里。

---

**结论和随之改的一处文案**

`透明` 档（不画）仍然是 App 这一侧唯一能碰到那道玻璃的姿势，但上面这句「App 侧没有可改的」的下半截要改成：**那道玻璃在公开 API 之外**——它有名字（`WidgetBackgroundStyle` / `CHSGlassOptions`），有参数，但没有任何一个能被第三方 App 编译期引用。改的是两点，都在 App 自己这一侧：

1. `FolderPlate.automatic` 的显示名从「跟随系统」改成「**透明**」。理由和对齐方式有关：WidgetLoft 的 Style 选择器是 Solid / Gradient / Transparent，我们的三档和它一一对应（纯色 / 渐变 / 透明），但名字不一样，对照两边的人得自己翻译。**磁盘上的值仍然是 `automatic`**——已经写过的 library 里存的就是它，schema 是契约。
2. 那一档的说明文案重写。上一版写的是「系统给小组件画的底板本身就是液态玻璃，会跟着壁纸变」，这句话比测量结果满：同一张图上 Apple 自己的组件也是纯白板。现在写的是「不自己画，整块交给系统；它跟着图标外观走，切到透明档时会被撤掉」，不带没量到的承诺。

## 免费 Apple ID 上真机跑，会缺哪一块

用户要连真机试。确认了账号是**免费 Apple ID**，所以先写清楚会发生什么。

### 已经确认的（不是推测）

在这台机器上把 `CODE_SIGN_ENTITLEMENTS=""` 建了一次，模拟了签名时 App Group 被拿掉的样子，然后直接读了二进制里嵌的 entitlements：

```
没有 App Group 时:
  application-identifier            FAKETEAMID.com.lvyufeng.appfolder
有 App Group 时:
  application-identifier            FAKETEAMID.com.lvyufeng.appfolder
  com.apple.security.application-groups  [ group.com.lvyufeng.appfolder ]
```

**App Group 是这里唯一的差别。** 其余部分（`UIApplication.open`、`canOpenURL` 探测、widget 渲染、`OpenURLIntent` 直开）都不依赖它。

另外确认了整个工程能**不带签名**编出 arm64 真机包（`CODE_SIGNING_ALLOWED=NO`），所以代码层面没有拦路的东西。

### 会缺什么

1. **桌面上那个小组件会是空的。** App 读不到 App Group 容器，`FolderStore` 走 `UserDefaults` 兜底，那份数据 widget 看不见。**这是免费的必然结果，不是 bug**——App Group 是跨进程共享的唯一通道，没有它就没有通道。
2. **图标会显示成空方块。** `IconStore` 原本会退到 App 自己的临时目录，App 读得好好的，只有 widget 读不到。也就是说**文件夹列表看起来完全正常，只有桌面是坏的**，最难查的那种。已经给它加了 `isCacheSharedWithWidget`，并在「排查」页写出来。
3. **探测已安装 App 不受影响。** `canOpenURL` 不看 App Group。
4. **中转（bounce）不受影响。** 走的是自定义 scheme + `onOpenURL`，同进程内的事。

### 所以

排查页在第一屏回答的就是这个问题：**「小组件能读到的文件夹数」**。如果是 0 而 App 里不是 0，原因就是共享存储，不用再猜。真机上装完先看这一行。

真机还能验的两件事（模拟器上都不行）：

- **液态玻璃**：把图标外观四档各切一次，看默认档下 widget 底板会不会跟着壁纸走。这一条在模拟器上验不了（理由见上面「默认档那一格，模拟器答不了」——那个偏好没有默认值以外的落盘位置，改它的 UI 在 SpringBoard 编辑态里，模拟器点不进去）。真机上是三步：长按桌面 → 编辑 → 自定，**先停在默认档**截一张，再切玻璃档截一张，比板内读数。要回答的只有一个问题：默认档那张，板内颜色跟着壁纸变了吗？
- **四个未验证的 scheme**：`ximalaya.mainapp://`、`fleamarket://`、`wemeet://`、`baiduboxapp://`——模拟器上一个第三方 App 都没装。

### 免费账号和开发者账号的差别（查证过的部分）

两个来源：Apple 自己的 [Compare Memberships](https://developer.apple.com/support/compare-memberships/)（免费档那一节的数字是原文引的），和 Xcode 自己的二进制（`IDEFoundation` 里有 `isFreeProvisioningTeam`、`IDEProvisioningProfileSupportRelaxed` 这类符号，说明 Xcode 内部就是把它当**降级档**处理的，且「App ID、设备、证书、描述文件都在 Xcode 里直接管」，不给进 Certificates, Identifiers & Profiles 门户）。

| | 免费（Personal Team） | 付费（Apple Developer Program） |
|---|---|---|
| 费用 | 0 | 每年 $99 |
| App ID | 最多 **10 个**，**7 天**过期 | 不限期 |
| 设备 | 最多 **3 台**，**7 天**过期 | 注册设备数按档位 |
| 每台设备上的 App | 最多 **3 个** | 无此限制 |
| 描述文件 | **7 天**过期，到期要**重新编译重装** | 一年 |
| **App Group** | **没有**（见下） | 有 |
| Push / iCloud / Background Modes 等 | 只有 [Supported capabilities](https://developer.apple.com/help/account/reference/supported-capabilities-ios) 里标了「Apple Developer」（免费）列的那几项 | 全量 |
| TestFlight / App Store Connect / Xcode Cloud / 公证 | **没有** | 有 |

那张能力对照表的两列是 ADP / ADEP / Apple Developer，文档只给了一句总则：「**The capabilities available to an iOS provisioning profile depend on your program membership.**」——逐行的勾选没有可靠的文本来源，所以我没往上抄。

**App Group 这条，我们的判断和公开资料一致，但我不把它写成苹果的原话。** 依据是两件事：Xcode 里对免费账号的描述是「Capabilities are not supported for …」，而 App Group 正是一项 capability；以及这台机器上把签名剥掉之后，嵌进二进制的 entitlements 里**唯一**消失的就是 `com.apple.security.application-groups`。所以结论是：**免费档上这个 App 的桌面小组件读不到数据，会是空的**——但这条要到真机上装一次才算真正验过。
